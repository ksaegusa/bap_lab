# ネットワーク監視設計

## 1. 目的

本監視では、ネットワーク機器およびネットワーク経路で発生する障害をZabbixで検知し、以下を実現する。

- 装置障害の検知
- Interface障害の検知
- BGP Neighbor障害の検知
- 通信経路障害の検知
- 通信品質劣化の検知
- 障害復旧の自動検知
- SNMP TrapとPollingを組み合わせた監視

監視対象はContainerlab上のFRR、GoBGP、SR Linux等のネットワークノードを想定する。

---

# 2. 監視方式

以下の方式を組み合わせる。

| 方式 | 用途 |
|---|---|
| SNMP Trap | 状態変化を即時検知 |
| SNMP Polling | 現在状態・カウンタの定期確認 |
| ICMP | 装置・経路の到達性確認 |
| BFD | Routing Protocolの高速障害検知 |
| Zabbix Trigger | 障害・復旧判定 |

SNMP Trapのみでは、装置自体が停止した場合にTrapを送信できない。

そのため、

```text
Trap
+
Polling
+
ICMP
```

を組み合わせる。

---

# 3. 監視レイヤ

ネットワーク障害を以下のレイヤに分けて監視する。

```text
Device
  |
Interface
  |
Link / Network Quality
  |
BFD
  |
Routing Protocol
  |
IP Reachability
```

障害によって、発生するイベントが異なる。

例えばPacket Loss障害では、

```text
Interface : UP
BFD      : DOWN
BGP      : DOWN
Reachable: DOWN
```

となる可能性がある。

一方、Interface自体をshutdownした場合は、

```text
Interface : DOWN
BFD      : DOWN
BGP      : DOWN
Reachable: DOWN
```

となる。

複数の監視情報を組み合わせることで、障害原因の切り分けを行う。

---

# 4. Device監視

## 4.1 ICMP Reachability

### 目的

ネットワーク機器自体が到達可能か確認する。

### 監視方式

ICMP Polling

### 障害条件例

```text
一定時間ICMP応答なし
```

例:

```text
30秒以上応答なし
→ PROBLEM
```

### 復旧条件

```text
ICMP応答再開
→ RECOVERY
```

### 検知対象

- 装置停止
- Management Network障害
- Routing障害
- Network Path障害

---

# 5. Interface監視

## 5.1 Interface Operational Status

主に以下を監視する。

```text
ifAdminStatus
ifOperStatus
```

### 状態例

```text
ifAdminStatus
1 = up
2 = down
3 = testing
```

```text
ifOperStatus
1 = up
2 = down
```

### 障害条件

```text
Admin UP
かつ
Oper DOWN
```

の場合にProblemとする。

これにより、意図的なshutdownと障害によるDownをある程度区別できる。

---

## 5.2 linkDown / linkUp Trap

Interface状態変化についてはSNMP Trapでも監視する。

### Down

```text
linkDown
```

### Up

```text
linkUp
```

動作:

```text
linkDown
↓
PROBLEM

linkUp
↓
RECOVERY
```

SNMP Pollingと組み合わせることで、

```text
Trap = 即時検知
Polling = 状態確認
```

とする。

---

# 6. Interface Traffic監視

Interface単位でトラフィック量を監視する。

主な監視項目:

```text
ifHCInOctets
ifHCOutOctets
```

これらから、

```text
Inbound bps
Outbound bps
Utilization %
```

を算出する。

### 利用目的

- 帯域逼迫検知
- トラフィック傾向確認
- 障害前後の通信量確認

---

# 7. Interface Error監視

主な監視項目:

```text
ifInErrors
ifOutErrors
ifInDiscards
ifOutDiscards
```

### 検知対象

- CRC等のInterface Error
- Buffer不足
- Congestion
- Packet Drop
- MTU等による異常

### Trigger例

```text
5分間でifInErrorsが100以上増加
```

または、

```text
Error rate > 一定値
```

でWarningとする。

---

# 8. BFD監視

BFDをRouting Protocolの高速障害検知に利用する。

例:

```text
Transmit Interval : 300ms
Receive Interval  : 300ms
Detect Multiplier : 3
```

この場合、概ね

```text
約0.9秒
```

で障害を検知できる。

処理:

```text
Packet Loss
↓
BFD Down
↓
BGP Neighbor Down
↓
SNMP Trap
↓
Zabbix PROBLEM
```

BGP Hold Timerだけに依存すると、デフォルト設定では障害検知に長時間かかるため、ラボではBFDを併用する。

---

# 9. BGP監視

## 9.1 BGP Trap

BGP4-MIBのTrapを利用する。

### BGP Established

```text
OID:
1.3.6.1.2.1.15.0.1
```

意味:

```text
BGP Neighbor Established
```

### BGP Backward Transition

```text
OID:
1.3.6.1.2.1.15.0.2
```

意味:

```text
BGP Neighborの状態が下位Stateへ遷移
```

実質的にNeighbor Down検知として利用する。

---

## 9.2 Zabbix Item

現在のTrap出力では以下の形式となる。

```text
SNMPv2-SMI::mib-2.15.0.1
SNMPv2-SMI::mib-2.15.0.2
```

そのためItemを以下とする。

```text
Name:
BGP state trap

Type:
SNMP trap

Key:
snmptrap["mib-2\.15\.0\.[12]"]

Type of information:
Log
```

---

## 9.3 BGP Trigger

例:

```text
find(/r2-frr/snmptrap["mib-2\.15\.0\.[12]"],,"like","mib-2.15.0.2")=1
```

動作:

```text
.15.0.2
↓
BGP Down
↓
Trigger TRUE
↓
PROBLEM
```

復旧時:

```text
.15.0.1
↓
BGP Established
↓
Down条件FALSE
↓
RECOVERY
```

---

# 10. BGP Polling監視

Trapだけでなく、BGP Neighbor StateをSNMP Pollingでも監視する。

目的:

```text
Trap取りこぼし対策
```

Trap:

```text
イベント発生時に即時通知
```

Polling:

```text
現在のBGP状態を定期的に確認
```

とする。

理想構成:

```text
BGP Trap
+
BGP State Polling
```

---

# 11. Neighbor単位の監視

現在のBGP TriggerはHost単位で最新Trapを判定している。

複数Neighborが存在する場合、

```text
Neighbor A Down
↓
.15.0.2
↓
PROBLEM

Neighbor B Established
↓
.15.0.1
↓
誤RECOVERY
```

となる可能性がある。

そのため最終的には、

```text
Trap OID
+
Peer IP
```

を組み合わせてNeighbor単位で管理する。

例:

```text
R2 → 10.0.1.0
R2 → 10.0.2.1
R2 → 10.0.4.1
```

それぞれ独立した障害として管理する。

---

# 12. Network Quality監視

InterfaceがUPのままでも通信品質が劣化する障害を検知する。

監視対象:

```text
Packet Loss
Latency
Jitter
Interface Errors
Interface Discards
```

Containerlabでは `tools netem` を利用して障害を再現できる。

例:

```bash
containerlab tools netem set \
  -n clab-bgp-chaos-r2-frr \
  -i eth2 \
  --loss 100
```

この場合、

```text
Interface Status = UP
Packet forwarding = Loss
```

となる。

BFDを併用することで、

```text
Packet Loss
↓
BFD Down
↓
BGP Down
↓
Zabbix検知
```

を確認する。

# 14. 監視優先度

初期段階では以下を実装する。

| 優先度 | 監視項目 | 方式 |
|---|---|---|
| 高 | Device Reachability | ICMP |
| 高 | Interface Up/Down | SNMP Trap + Polling |
| 高 | BGP Neighbor Up/Down | SNMP Trap |
| 高 | BGP Neighbor State | SNMP Polling |
| 高 | BFD State | Routing/BFD監視 |
| 中 | Interface Errors | SNMP Polling |
| 中 | Interface Discards | SNMP Polling |
| 中 | Interface Traffic | SNMP Polling |
| 中 | Packet Loss | ICMP / Probe |
| 中 | Latency | ICMP / Probe |
| 低 | CPU | SNMP Polling |
| 低 | Memory | SNMP Polling |
| 低 | Temperature | SNMP Polling |
| 低 | Fan | SNMP Polling |
| 低 | PSU | SNMP Polling |

# 17. 監視設計の基本方針

単一の監視方式だけで障害を判断しない。

例えば、

```text
Interface DOWN
+
BFD DOWN
+
BGP DOWN
```

ならInterface障害の可能性が高い。

一方、

```text
Interface UP
+
BFD DOWN
+
BGP DOWN
```

ならPacket Lossや経路障害の可能性が高い。

また、

```text
ICMP DOWN
+
SNMP DOWN
+
複数NeighborからBGP DOWN
```

なら装置障害の可能性が高い。

最終的には複数の監視項目を相関させ、

```text
「何が落ちたか」
```

だけでなく、

```text
「なぜ落ちた可能性が高いか」
```

まで判断できる監視構成を目指す。
